# Управление и решение проблем

## Архитектура развертывания

Фронтенд WebUI предоставляется через Python-контроллер, который находится в той же областью, что и REST-и MCP-端点ы. База данных по умолчанию использует SQLite. В выпущенных бинарных форматах также включены компилированные файлы фронтенда. Для сборки из исходного кода необходимо использовать инструменты для компиляции JavaScript. Не требуется использование Node.js, MongoDB, Meilisearch или других серверов.

Используйте описания в разделах [Быстрое начало](../getting-started/quickstart.md) и [Рекомендации по настройке](../reference/configuration.md). Для создания проектов из исходного кода обратитесь к инструкциям, находящимся в [WebUI](https://github.com/fwerkor/local-shell-mcp/blob/main/ui/workspace/README.md).

## Обеспечить успешную развертывание

Используйте надежный обратный прокси-сервер или туннель, работающий по протоколу HTTPS. Обеспечьте аутентификацию и использование强ых паролей для доступа к сервисам. Храните объект Controller в соответствующем контейнере или внутри виртуальной машины. Ограничьте доступ извне, а также защищайте данные, передаваемые наружу. Не размещайте незащищенные точки доступа в публичном Интернете.

Прокси-сервер должен поддерживать потоковые ответы без необходимости блокировки их до завершения обработки. Также необходимо поддерживать использование протокола WebSocket для интерфейсов, которые этого требуют. Необходимо использовать подходящие временные ограничения для чтения данных и времени ожидания при выполнении запросов к долгим моделям и инструментам. Условия загрузки данных должны соответствовать настройкам публичного URL-адреса, а также параметрам OAuth-связи. Не следует отменять проверку сертификатов TLS в целом, чтобы не допустить ошибок при использовании протокола TLS.

Запросы, связанные с моделями, исходят из Controller. Месседжи, приложения и результаты обработки данных могут быть отправлены в выбранный API. Перед использованием конфиденциальной информации необходимо тщательно проверить условия обработки данных со стороны поставщика услуг. Также необходимо защищать внешние секреты MCP и токены для приглашений от Worker.

## Состояние системы, резервные копии и обновления

Подробная информация о состоянии системы хранится в директории `.local-shell-mcp`, которая находится внутри настроенной рабочей области. Значение переменной `LOCAL_SHELL_MCP_STATE_DIR` может изменять это значение. Общая база данных имеет название `lsm.sqlite3`. Чаты, проекты, настройки, агенты, информация о времени выполнения задач и другие данные хранятся на сервере. Адреса приложений, файлы рабочей области и другие данные могут находиться вне базы данных.

Соберите полный список резервных копий состояния системы, включая данные, хранящиеся вне самого каталога состояния, а также информацию о среде развертывания и секретах, необходимых для работы системы. Считайте резервные копии конфиденциальными данными. Резервная копия, содержащая только базу данных, может не включать приложения или параметры конфигурации. Используйте механизм резервного копирования, который обеспечивает постоянную доступность данных. Копирование только основной базы данных SQLite может не включать информацию о записах, произведенных в процессе работы системы. Проверьте резервные копии, восстановив их в изолированной тестовой среде.

Перед обновлением запишите текущую версию программы, путь к исполнению скриптов, параметры конфигурации, местоположение активных задач и т. д. Затем прекратите выполнение всех соответствующих процессов или безопасно выгрузите все необходимые данные. Сделайте сравнимую резервную копию всей установки. После обновления проверьте все параметры, историю переписок, процесс генерации моделей, функции передачи данных, а также задачи, выполняемые в режиме реального времени. Миграция данных из старой версии в новую поддерживается при запуске программы. Сохраняйте старые файлы до тех пор, пока не убедитесь в успешности миграции. Не заменяйте директорию, в которой хранятся производственные данные, на пустую директорию для тестирования.

Откат не означает простое изменение бинарных файлов, если состояние базы данных изменилось в результате миграции. Необходимо восстановить совместимое состояние, когда это необходимо. Также следует избегать использования двух контроллеров с разными настройками для одного и того же хранилища данных.

## Диагностика несовершенной работы чата.

| Симптомы проблемы. | Проверка сначала. |
|---|---|
| Невозможно загрузить интерфейс пользователя. | Процесс управления контроллером, фреймворк для клиентского интерфейса, правильный URL-адрес, прокси-сервер и механизмы аутентификации |
| Отсутствие модели. | Конфигурация канала, идентификация модели, авторизация пользователя. |
| HTTP 401/403 от провайдера. | Ключ API/учетные данные, разрешения провайдера, выбранный канал и протокол. |
| HTTP 429 | Ограничения скорости передачи данных, количество одновременных запросов, статус учета/плана. |
| HTTP 400/413/422 | Совместимость запросов, размер входных данных/контекста, ограничения на приложения, параметры модели. |
| Ошибка HTTP 5xx или тайм-out. | Состояние провайдера, сетевые условия, способность сервера обслуживать запросы, таймеры прокси-сервера. |
| Процесс вывода данных прекращается. | Необходимо восстановить соединение/перезагрузить систему; необходимо проверить статус генерации данных и подробную информацию о возникших ошибках. |
| Инструмент недоступен. | Функциональные возможности, способности агентов, правила ACL на машине, ограничения по OAuth-сценариям, переключение режимов контроллера |
| Работник находится в состоянии офлайн. | Регистрация работников, установление соединений, отправка сигналов „хаартиб“ и логи Controller. |
| Процедура находится в стадии утверждения/рассмотрения. | Необходимо открыть диалог и проверить запрашиваемые действия. |
| Задание не выполняется. | Состояние активации, часовой пояс, агент/канал связи, целевая информация, сохраненные разрешения, последний запуск процедуры. |

Не следует полагать, что все ошибки HTTP происходят из одного и того же сервиса. Необходимо различать неудачу сессии LSM, ошибку в API-сервисе, внешнюю ошибку MCP и ошибку в процессе передачи данных. Проверяйте подробные сообщения об ошибках, а также логи контроллера. Необходимо скрывать ключи, токены и URL-адреса для возврата данных перед их использованием.

## Попытки восстановления и ресурсы провайдера

До начала ответа модели временные ошибки подключения и некоторые ошибки HTTP (408, 429, 500, 502, 503, 504) допускают повторные попытки с ограниченной задержкой. Текущие стандартные задержки составляют 1, 2, 4, 8, 16, 30, 30 и 30 секунд (восемь повторов после исходного запроса). HTTP Retry-After может увеличить задержку до 120 секунд; некоторые ошибки потоковой передачи добавляют случайное отклонение. Лимит повторов действует на отдельный запрос модели, а не на весь чат. Компактификация имеет собственный путь восстановления. Ограничение из-за исчерпания кредитов может сохраняться до пополнения квоты провайдером. Автоматические повторы не гарантируют успеха и не делают подписку безлимитной.

Прерывание процесса в середине его выполнения отличается от ошибки, произошедшей до момента первого ответа на запрос пользователя. Не следует полагаться на автоматическое повторное выполнение частично завершенного процесса. Перед повторным запуском необходимо проверить сохраненные данные и внешние параметры системы. Если процесс все еще активен, следует снова попробовать его выполнение, а не начинать процесс заново. Если процесс завершился неудачей, следует использовать функции восстановления или повторного запуска процесса, или начать новый процесс с нуля, если первый процесс не может продолжаться.

Обладающие проблемами с компактификацией контекста, следует рассматривать отдельно от обычных ошибок при генерации моделей. Необходимо проверить эффективный лимит контекста, совместимость моделей, объем результатов, получаемых с помощью инструментов, а также доступные квоты. См. раздел [Память и контекст](context.md).

## Что следует включать в отчет о багах

Укажите версию и комитет LSM, способ установки, операционную систему, тип протокола, тип защищенного endpoints, идентификатор модели, приблизительное время, шаги воспроизведения проблемы, соответствующие данные о чате/работе, а также подробную информацию о возникших ошибках. В случае удаленной проблемы укажите версию рабочего процесса, имя машины, а также статус сигналов и обновлений. При возможности приведите пример воспроизведения проблемы. Никогда не отправляйте API-ключи, токены OAuth, личную информацию или другую ненужную персональную данные.
