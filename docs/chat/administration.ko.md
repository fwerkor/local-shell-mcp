# 관리 및 문제 해결

## 배포 아키텍처

WebUI 프론트엔드는 Python 컨트롤러에서 제공되며, REST 및 MCP 엔드포인트와 동일한 원본에서 실행됩니다. 기본 상태 저장소는 SQLite입니다. 배포된 바이너리 파일에는 컴파일된 프론트엔드 자산도 포함되어 있습니다. 소스 코드를 직접 빌드하려면 JavaScript 빌드 도구가 필요하며, 설치된 컨트롤러는 필요하지 않습니다. Node.js, MongoDB, Meilisearch, 그리고 별도로 배포된 LibreChat 백엔드는 필요하지 않습니다.

[빠른 시작](../getting-started/quickstart.md)과 [구성 참조](../reference/configuration.md)를 활용하세요. 소스 코드를 사용하여 빌드할 경우, [WebUI 빌드 지침](https://github.com/fwerkor/local-shell-mcp/blob/main/ui/workspace/README.md)을 참고하십시오.

## 안정적인 배포를 보장하기

신뢰할 수 있는 HTTPS 리버스 프록시나 터널을 사용해야 합니다. 또한, 인증 및 강력한 비밀번호도 필요합니다. Controller는 적절한 컨테이너나 가상 머신 내부에 유지해야 합니다. 들어오는 접근을 제한하고, 나가는 정보도 보호해야 합니다. 인증되지 않은 엔드포인트는 공개 인터넷에 노출해서는 안 됩니다.

프록시는 데이터를 버퍼링하지 않고 즉시 반환할 수 있어야 합니다. 또한, WebSocket 프로토콜을 지원해야 하며, 그러한 기능이 필요한 인터페이스들도 지원되어야 합니다. 긴 시간 동안 데이터를 처리해야 하는 경우에는 적절한 읽기/대기 시간을 설정해야 하며, 원하는 업로드 크기도 허용되어야 합니다. 설정된 공개 URL은 브라우저의 원본 주소와 OAuth 콜백과 일치하도록 해야 합니다. TLS 오류를 전 세계적으로 처리하기 위해 인증서 검사를 비활성화해서는 안 됩니다.

요청은 Controller에서 발생하며, 모델에 표시되는 메시지, 첨부 파일, 도구의 결과물들은 선택된 업스트림 API로 전송될 수 있습니다. 기밀 정보를 사용하기 전에는 제공자의 데이터 처리 방식에 대해 반드시 확인해야 합니다. 외부의 MCP 비밀번호와 Worker 초대 토큰도 보호해야 합니다.

## 상태, 백업, 업그레이드

기본 상태 디렉터리는, 구성된 작업 공간 아래에 있는 `.local-shell-mcp`입니다. `LOCAL_SHELL_MCP_STATE_DIR`을 변경할 수 있습니다. 공유 데이터베이스는 `lsm.sqlite3`입니다. 채팅 내용, 프로젝트, 설정, 에이전트, 메모리, 스케줄 및 실행 상태 등은 서버에 저장됩니다. 첨부 파일, 작업 공간의 파일들 및 기타 자료들은 데이터베이스 외부에 저장될 수 있습니다.

전체 상태 디렉토리를 백업해 주세요. 그 외에 구성된 상태도 함께 백업해야 합니다. 또한, 배포 환경/비밀번호 및 관련 작업 공간 파일들도 백업해야 합니다. 백업 자료는 매우 민감한 정보이므로 조심스럽게 처리해야 합니다. 데이터베이스만을 위한 백업의 경우, 첨부 파일이나 구성 정보가 누락될 수 있습니다. Controller를 사용하거나 일관된 SQLite 백업 메커니즘을 활용하는 것이 좋습니다. 실제 운영 중인 SQLite 데이터베이스 파일만 복사하면, 커밋된 WAL 내용이 누락되는 것을 방지할 수 있습니다. 백업된 자료가 제대로 작동하는지 확인하기 위해, 격리된 테스트 환경에서 다시 복원해 보세요.

업그레이드를 진행하기 전에, 현재 버전, 실행 경로, 설정 정보, 활성화된 작업들 등을 기록해 두세요. 관련된 작업들을 중단시키거나 안전하게 종료시킨 후, 일관된 백업을 만들어야 합니다. 그런 다음 동일한 설치를 업그레이드하고, 인증 정보, 채팅 기록, 모델 생성 과정, 스트리밍 기능, Workers 및 예약된 작업들도 확인해야 합니다. 이전 상태에서 SQLite 데이터를 마이그레이션하는 기능도 지원됩니다. 마이그레이션이 완료될 때까지 기존 파일들을 그대로 유지해 두세요. 실제 데이터 디렉토리를 비어 있는 테스트용 디렉토리로 대체하지 마세요.

롤백은 단순히 데이터베이스 마이그레이션으로 인해 변경된 상태를 다시 복원하는 것만을 의미하지 않습니다. 필요할 때는 호환 가능한 상태로 되돌릴 수 있도록 해야 합니다. 또한, 동일한 실제 저장소에 두 개의 별도로 구성된 컨트롤러를 실행하는 것은 피해야 합니다.

## 실패한 채팅을 진단합니다.

| 증상/현상 | 먼저 확인해보세요. |
|---|---|
| UI를 로드할 수 없습니다. | 컨트롤러 프로세스, 프론트엔드 번들, 올바른 URL, 프록시 및 인증 |
| 모델이 없습니다. | 채널 구성, 모델 발견, 모델 ID, 계정 권한 설정 |
| 공급자로부터 HTTP 401/403 상태 코드가 전송되었습니다. | API 키/계정, 제공자의 권한, 선택된 채널 및 프로토콜 |
| HTTP 429 | 상류의 요금/할당량 제한, 동시 요청 수, 계정/플랜의 상태 |
| HTTP 400/413/422 | 호환성에 대한 요청, 입력/컨텐츠의 크기, 첨부 파일의 제한 사항, 모델 매개변수 등에 대한 정보를 제공해 주세요. |
| HTTP 5xx 또는 타임아웃 현상 | 제공자의 상태, 네트워크 상태, 모델의 서비스 능력, 프록시의 타임아웃 현상 |
| 출력 내용이 스트리밍을 중단함 | 재연결/리로드 처리; 생성된 데이터의 상태와 세부적인 오류 정보 확인 |
| 도구가 사용할 수 없음 | 기능 활성화/비활성화, Agent의 기능, 머신 ACL, OAuth 범위, Controller의 스위치 설정 |
| Worker가 오프라인 상태임 | Worker의 등록, 외부 연결, 하트비트, Controller의 로그 정보 |
| 승인이 필요한 경우/문제가 있는 경우 | 대화를 열고 요청된 작업을 확인함 |
| 스케줄이 실행되지 않음 | 활성 상태, 시간대, Agent/채널, 대상, 저장된 권한 정보, 최근 실행 기록 |

모든 HTTP 오류가 같은 서비스에서 발생하는 것은 아니라는 점을 명심하세요. LSM 로그인 실패, 업스트림 모델 API 오류, 외부 MCP 오류, 그리고 워커 전송 오류 등을 구분해야 합니다. 세부적인 오류와 관련된 컨트롤러 로그도 확인해야 합니다. 또한, 키, 베어러 토큰, 콜백 URL 등은 공유하기 전에 반드시 비공개로 처리해야 합니다.

## 프로바이더의 재시도 및 복구 과정

모델 응답이 시작되기 전에 발생한 일시적인 연결 오류와 일부 HTTP 오류(408, 429, 500, 502, 503, 504)는 제한된 대기 시간으로 재시도할 수 있습니다. 현재 일반적인 재시도 대기 시간은 1, 2, 4, 8, 16, 30, 30, 30초입니다(최초 요청 이후 8회 재시도). HTTP Retry-After는 대기 시간을 최대 120초까지 늘릴 수 있으며 일부 스트리밍 오류에는 무작위 변동이 추가됩니다. 재시도 한도는 전체 채팅의 누적 횟수가 아니라 개별 모델 요청에 적용됩니다. 컨텍스트 압축은 자체 복구 경로를 갖습니다. 크레딧 소진에 따른 요청 제한은 제공자가 할당량을 보충할 때까지 지속될 수 있습니다. 자동 재시도가 성공을 보장하거나 구독을 무제한으로 만들지는 않습니다.

중간에 중단된 경우는, 첫 번째 응답이 발생하기 전의 오류와는 다릅니다. 부분적으로 실행된 도구 순서를 자동으로 다시 실행할 수 없습니다. 재시도하기 전에 저장된 기록과 외부 상태를 확인해야 합니다. 만약 실행이 여전히 진행 중이라면, 중복된 작업을 시작하는 대신 다시 연결해야 합니다. 만약 실행이 실패했다면, 채팅 복구/재시도 기능을 적절히 사용하거나, 원본 작업이 계속할 수 없다면 새로운 채팅을 시작해야 합니다.

컨텍스트 압축 관련 오류는 일반적인 모델 생성 오류와는 별도로 조사해야 합니다. 효과적인 컨텍스트 제한, 모델의 호환성, 과도하게 큰 도구 결과물, 사용 가능한 할당량 등을 확인해 주세요. 자세한 내용은 [메모리 및 컨텍스트](context.md)를 참조하십시오.

## 버그 보고서에 무엇을 포함해야 하는가?

LSM 버전/커밋, 설치 방법, 운영체제, 모델 프로토콜, 정리된 엔드포인트 유형, 모델 ID, 대략적인 시간, 재현 단계, 관련 채팅/실행 상태, 그리고 세부적인 오류 내용을 보고해야 합니다. 원격 문제의 경우, Worker 버전, 머신 이름, 하트비트/폴링 상태도 함께 포함해야 합니다. 가능하다면 간단한 재현 과정도 함께 제공해 주세요. API 키, OAuth 토큰, 개인 정보 등은 절대로 전송해서는 안 됩니다.
