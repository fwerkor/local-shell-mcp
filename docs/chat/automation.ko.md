# 목표들, 예정된 대화들, 그리고 장기적으로 진행되어야 할 작업들

## 올바른 메커니즘을 선택하세요.

| 메커니즘 | 목적 |
|---|---|
| 일반적인 채팅 생성 | 현재의 요청에 응답하며, 관련 도구를 호출할 수도 있습니다. |
| 채팅 목표 설정 | 모델의 전환 구간을 넘어서도 활발한 논리적 세션을 계속 유지합니다. |
| 예약된 채팅 | 저장된 프롬프트를 사용하여, 반복적인 주기로 작동하는 Agent를 시작합니다. |
| 지속적인 작업 또는 터미널 기능 | 단일 모델 요청과는 독립적으로 명령을 실행할 수 있습니다. |
| 하위 에이전트 | 제한된 작업을 다른 Agent 스레드에게 위임할 수 있습니다. |

예약된 채팅은 지속적인 셸 작업이 아닙니다. 논리적 세션도 실제로는 대화나 운영 체제의 프로세스가 아닙니다. 세션을 취소한다고 해서, 그 세션에서 시작된 모든 작업이 반드시 종료되는 것은 아닙니다.

## 채팅 목표 설정

긴 작업을 처리할 경우, Agent에게 구체적인 목표를 설정하도록 요청해야 합니다. 또한, Logical Session 도구를 사용하여 계획을 유지 관리해야 합니다. 이 계획에는 각 단계와 그 상태가 기록됩니다. 채팅 실행 환경에서는 모델의 전환 시점에 활성화된 계획을 계속 진행할 수 있으며, 새로운 사용자의 요청이나 외부 MCP Live Workspace의 비활동 타이머를 기다릴 필요가 없습니다.

계획과 진행 상황을 확인한 후, 사용 가능한 목표 제어 기능을 통해 일시 중지, 재개 또는 취소할 수 있습니다. 계속 진행하려면 활성화된 계획과 적합한 상태의 실행이 필요합니다. 이미 완료되었거나 차단된 계획은 계속 진행될 수 없습니다. 동일한 반응이 반복되는 경우, 무한 루프가 발생하는 대신 일시 중지됩니다(현재는 세 번째로 변하지 않는 경계 조건에서 이런 현상이 발생합니다). 재개하기 전에 실제적인 방해 요소를 해결해야 합니다.

완료 기준을 명확히 정의해야 합니다. 예를 들어, 리포지토리를 검사하고, 필요한 수정 사항을 적용하며, 관련된 테스트를 실행하여 실패 사항을 보고하는 것입니다. Agent에게는 단순히 자신의 계획에 따라 성공 여부를 판단하기보다는, 정확한 커밋 ID와 테스트 결과를 기록하도록 요청해야 합니다.

외부의 MCP 클라이언트 목표 메커니즘은 별개입니다. Logical Session 및 라이브 워크스페이스 전환 프로세스에 대해서는 [Human interface](../guides/human-interface.md)을 참조하십시오.

## 예약된 채팅 기능을 만들어보세요.

![비활성화된 예제 일정을 표시하는 예약 채팅 사이드바](../assets/chat/scheduled-chats.png)

예약된 채팅 관리 기능을 열어보세요. 설명이 적힌 이름을 가진 예약을 생성합니다. 에이전트를 저장하고, 프롬프트, 시간대, 진행 빈도 등을 설정합니다. 대화의 대상을 선택할 수 있으며, 필요하다면 새로운 대화를 위한 프로젝트도 선택할 수 있습니다. 설정을 저장한 후 예약된 채팅 기능을 활성화합니다. 실제로 사용하기 전에 수동으로 설정을 확인해보세요.

지원되는 실행 주기는 시간당, 매일, 평일, 주별, 5개 필드를 기준으로 하는 크론 등이 있습니다. 연속적인 실행은 설정된 지연 시간 이후에 다시 시작됩니다. 지연 시간을 0으로 설정하면 지속적으로 서비스가 제공될 수 있습니다. 일반적인 반복적인 스케줄은 최소 5분의 간격을 요구합니다. `Asia/Shanghai`나 `UTC`와 같은 명확한 IANA 시간대를 사용해야 합니다. 저장 후 다음 실행 시기를 확인해보세요.

평일 09:00에 실행하는 cron 예시:

```text
0 9 * * 1-5
```

이 경우, 선택된 시간대가 사용됩니다. 반드시 Controller의 시스템 시간대와 일치하는 것은 아닙니다. 선택된 시간대가 일광절약제를 적용하는지 확인해 주세요.

## 대화의 대상들

- **매번 새 대화:** 각각의 경우마다 별도의 대화를 시작할 수 있습니다. 이는 개별적인 보고서를 작성하는 데 유용합니다.
- **같은 대화 재사용:** 처음에 진행된 대화 내용을 저장해두고, 이후에도 같은 대화를 다시 사용할 수 있습니다. 이는 누적적인 모니터링에 유용합니다.
- **기존 대화 사용:** 예약된 순서에 따라 대화가 진행될 수 있는 기존의 채팅방을 선택하세요.

재사용된거나 기존의 대화 내용은 더욱 발전시켜야 하며, 압축이 필요할 수도 있습니다. 역사적 맥락이 불필요한 경우에는 별도의 채팅을 사용하는 것이 좋습니다. 예약된 실행은 선택된 에이전트와 모델 채널이 여전히 존재하고 사용 가능한지에 따라 달라집니다.

## 무단으로 부여된 권한들

예약 실행은 Controller가 관리하며 브라우저 로그인 토큰을 보관하는 대신 저장된 인가 범위 이름을 사용합니다. 필요한 경우 예약을 저장하거나 수동 실행하여 인가하세요. 지정된 Agent의 머신 권한이 적용되며 일반 프로젝트 또는 채팅의 머신 재정의 설정은 예약의 머신 정책이 아닙니다. Controller 제한, 저장된 인가, 도구 기능 및 도구 승인은 계속 적용됩니다.

인증이 필요한 외부 MCP 서버의 경우 대화형 로그인만으로 무인 실행을 위한 갱신 가능한 권한이 자동으로 부여되는 것은 아닙니다. 예약 화면에서 재인증 또는 무인 접근이 필요하다고 표시되면 예약을 활성화하기 전에 서버별 자격 증명을 해결하거나 해당 의존성을 제거하세요. 브라우저 토큰을 대신 사용하지 마세요.

모니터링에는 읽기 전용인 에이전트를 사용해야 합니다. 허용될 수 있는 대상, 원하는 출력 결과, 그리고 피해야 할 조치들을 명확하게 설명해야 합니다. 만약 예약된 작업에 인간의 개입이나 승인이 필요하다면, 진행 중인 작업들을 주의 깊게 확인해야 합니다. 무인 상태로 작업이 수행된다고 해서 무제한적인 접근이 가능하다고 가정해서는 안 됩니다. 모니터링 프롬프트의 예시는 다음과 같습니다:

```text
지정된 훈련 작업과 그에 관련된 로그들을 확인해 보세요.
현재 진행 중인 단계, 손실량, 처리 속도, 예상 도착 시간, 그리고 발생한 새로운 오류들에 대해 보고합니다.
파일을 수정하지 마시고, 작업을 다시 시작하거나 새로운 작업을 시작하지 마세요.
만약 데이터가 없다면, 그 이유를 정확히 기재해 주세요.
```

## 생명주기와 복구 과정

Controller는 스케줄과 실행 상태, 그리고 발생한 이벤트들을 트랜잭션 방식으로 저장합니다. 이를 통해 중복된 작업이 발생하는 것을 방지할 수 있습니다. 브라우저 탭을 계속 열어두어야 할 필요는 없습니다. 놓친 이벤트들이 항상 다시 실행된다는 것, 혹은 Controller가 재시작하더라도 모든 외부 작업이 그대로 유지된다는 것을 가정하지 마세요. 다운타임 후에는 마지막으로 실행된 작업, 다음에 실행될 작업, 그리고 관련된 채팅 내용을 확인해야 합니다.

미래에 자동으로 발생할 일들을 방지하기 위해 스케줄을 비활성화해야 합니다. 이미 실행 중인 스케줄은 별도로 확인해야 합니다. 미래의 스케줄링을 중단한다고 해서, 실제로 진행 중인 작업이나 셸 작업이 취소된다는 보장은 없습니다. 더 이상 필요하지 않은 스케줄들은 삭제하고, 불필요한 에이전트 권한도 취소해야 합니다.

WebUI Agent에 의해 생성된 작업이나 터미널은, 일반적인 모델 반응 과정이 완료된 후에도 계속 존재할 수 있습니다. 따라서 Controller가 재시작된다 해도 반드시 그 작업이 종료되는 것은 아닙니다. 명시적인 취소나, 머신 권한의 상실, 또는 권한의 만료와 같은 상황이 발생하면, Agent가 소유한 작업이 취소될 수 있습니다. 만약 Worker가 오프라인 상태라면, 작업이 완료될 때까지는 취소된 상태로 남아 있을 수 있습니다. 작업이나 터미널이 더 이상 실행되고 있지 않다고 선언하기 전에, 그 자체를 확인해야 합니다. Agent는 보호된 WebUI 도구를 통해 자신이 소유한 작업/쉘을만 전송하거나 중단시킬 수 있습니다. 외부 MCP 클라이언트들은 자신의 기존 semantics를 유지합니다.

에이전트의 백그라운드 도구와 서브에이전트 작업들은 각각 고유한 라이프사이클을 가지고 있습니다. 작업이 완료된 후에도 결과가 아직 전달되지 않을 수도 있습니다. 따라서 대화의 백그라운드 작업 패널을 확인하여 결과를 수집하거나, 설정된 웨이크업 기능을 사용하여 부모 작업을 다시 시작해야 합니다. 결과가 아직 표시되지 않았다고 해서 중복된 작업을 시작해서는 안 됩니다.

개별 도구의 요청보다 더 오래 지속되어야 하는 명령어들의 경우, LSM을 사용하여 작업을 추적하거나, 영구적인 터미널을 사용해야 합니다. 출력 결과를 로그 파일에 저장하고, 작업 식별자를 기록하며, 실제 진행 상황을 확인해야 합니다. 자세한 내용은 [사용 패턴](../guides/usage-patterns.md)을 참조하십시오.
