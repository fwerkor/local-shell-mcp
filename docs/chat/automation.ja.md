# 目標、予定されているチャット、そして長期的に続く作業

## 正しいメカニズムを選びましょう。

| メカニズム | 目的 |
|---|---|
| 通常のチャット生成 | 現在のプロンプトに応答するため、ツールの呼び出しも行う。 |
| チャットの目的を定める。 | モデルの処理の境界を超えて、活動的なロジカルセッションを継続する。 |
| スケジュールされたチャット | 保存されたプロンプトを使って、定期的に実行されるエージェントを起動します。 |
| 永続的なジョブやターミナル処理を行う。 | 単一のモデルリクエストとは無関係にコマンドを実行する。 |
| サブエージェント | バウンド化されたタスクを、別のエージェントスレッドに委任する |

スケジュールされたチャットは、持続的なシェルジョブではありません。論理セッションも、会話やOSプロセスではありません。セッションをキャンセルしても、そのツールによって開始されたすべての処理が必ずしも終了するわけではありません。

## チャットの目的を定める。

長期的な作業の場合は、エージェントに具体的な目標を定義させ、Logical Sessionツールを使って計画を維持させます。この計画には、各ステップとその状態が記録されます。チャット実行環境では、新しいユーザーの入力や外部のMCP Live Workspaceの非活動時間を待つことなく、モデルのターン間でアクティブな計画を継続させることができます。

計画や進捗状況を確認し、利用可能なゴールコントロールを使って、実行を一時停止したり、再開したり、キャンセルしたりすることができます。計画が有効であり、実行可能である場合にのみ、計画を続行できます。既に完了した、ブロックされた、またはキャンセルされた計画では、計画を続行することはできません。進捗がないまま繰り返し同じような回答をしても、無限ループになることはありません（現在は、3回連続で変更されていない境界条件が発生した場合にのみ無限ループが発生します）。再開する前に、実際の障害を解決してください。

完了基準を定義しましょう。例えば、リポジトリをチェックし、修正を行い、関連するテストを実行し、失敗があれば報告することです。エージェントには、単に自分の計画通りに進んだとだけ報告するのではなく、正確なコミットIDやテスト結果を記録させるべきです。

外部のMCPクライアントのゴールメカニズムは、別途存在します。論理的なセッションやライブワークスペースの移行に関するワークフローについては、[Human interface](../guides/human-interface.md)を参照してください。

## スケジュールされたチャットを作成する

![無効にしたサンプルのスケジュールを表示するサイドバー](../assets/chat/scheduled-chats.png)

スケジュールされたチャットの管理を開きます。説明が記載されている名前を持つスケジュールを作成します。エージェントの設定、プロンプト、タイムゾーン、実行頻度も指定します。対話の対象を選択し、新しい会話のためにプロジェクトを選択することもできます。スケジュールを保存して有効にします。実際にスケジュールを使用する前には、手動で設定を確認してください。

サポートされているカデンスには、1時間ごと、1日ごと、平日のみ、週単位、5フィールドのクロンなどがあります。連続実行は、設定された遅延時間後に再び実行されます。ゼロの遅延を設定すると、持続的なプロバイダーやマシンの負荷が発生します。通常の定期実行スケジュールでは、最低5分間隔が必要です。`Asia/Shanghai`や`UTC`といった明確なIANAタイムゾーンを使用してください。保存後に表示される次回の実行内容を確認してください。

平日の 09:00 に実行する cron の例：

```text
0 9 * * 1-5
```

この場合、使用されるのは選択されたタイムゾーンであり、必ずしもControllerのシステムタイムゾーンとは一致するわけではありません。選択されたタイムゾーンが夏時間を採用している場合は、その変更点について確認してください。

## 会話の対象となる人々

- **毎回新しい会話:** 各場合について、別々の会話を開始することができます。これは、個別の報告を行う際に便利です。
- **同じ会話を再利用:** 最初の実行時に会話を作成し、その後も同じ会話を再利用することができます。これは、累積的なモニタリングに役立ちます。
- **既存の会話を使用:** スケジュールされた順番で会話が行われる、既存の会話を選びます。

再利用された、または既存の会話は、さらに発展させる必要があります。歴史的な背景が不要な場合は、独立したチャットを選ぶべきです。スケジュールされた実行は、選択されたエージェントやモデルチャンネルが依然として存在し、使用可能であるかどうかに依存します。

## 無監視の権限設定

スケジュール実行は Controller が管理し、ブラウザーのログイントークンを保持する代わりに、保存された認可済みスコープ名を使用します。必要な場合はスケジュールを保存するか手動で実行して認可してください。指定された Agent のマシン権限が適用され、通常のプロジェクトやチャットのマシン上書き設定はスケジュールのマシンポリシーにはなりません。Controller の制限、保存された認可、ツールの機能、ツール承認も引き続き適用されます。

認証を必要とする外部 MCP サーバーでは、対話的にログインしても、無人実行のための更新可能な認可が自動的に付与されるわけではありません。スケジュール画面で再認証や無人アクセスが必要と表示された場合、スケジュールを有効にする前にサーバー固有の認証情報を整えるか、依存関係を削除してください。ブラウザートークンで代用しないでください。

監視には、読み取り専用のAgentを使用します。許可されるターゲット、必要な出力内容、および行うべき操作を明確に指定します。スケジュールされたタスクに人的な介入や承認が必要な場合は、待機中のインタラクションを確認してください。無制限のアクセスがあると仮定してはいけません。監視プロンプトの例：

```text
指定されたトレーニングジョブとそのログを確認します。
現在のステップ、損失、スループット、到着予定時間、および新たに発生したエラーを報告します。
ファイルを変更したり、ジョブを再起動したり、新しい作業を開始したりしてはいけません。
データが利用できない場合は、その理由を正確に報告してください。
```

## ライフサイクルと復旧処理についても注意してください。

Controllerは、スケジュールや実行状態、および発生したトランザクションをトランザクションベースで保存します。これにより、重複した実行が発生するのを防ぎます。ブラウザのタブを開いたままにしておく必要はありません。また、失われたイベントが必ず再実行されるわけではなく、また、Controllerが再起動してもすべての外部処理が維持されるわけでもありません。ダウンタイム後に、最後の実行内容や次回の実行内容、実行中の処理内容、および関連するチャット内容を確認してください。

将来の自動実行を防ぐために、スケジュールを無効にします。既に実行中のスケジュールについては、別途確認する必要があります。将来のスケジュールを停止しても、実際に実行されている作業がキャンセルされるわけではありません。不要になったスケジュールを削除し、不要なエージェントの権限も取り消すべきです。

WebUIエージェントによって作成されたジョブやターミナルは、通常のモデル応答が完了した後でも存続することがあります。また、コントローラーの再起動だけでは、必ずしもそのジョブやターミナルを終了させるわけではありません。明示的な中止や、マシンの権限の喪失、または許可の有効期限切れなどがあれば、エージェントが管理する作業がキャンセルされる可能性があります。もしワーカーがオフライン状態であれば、そのジョブやターミナルが実行を停止するまで、キャンセル処理が保留状態になります。実行が停止したと宣言する前に、そのジョブやターミナル自体を確認する必要があります。エージェントは、保護されたWebUIツール経由でのみ、自分自身が管理するジョブやシェルを送信したり、停止したりすることができます。外部のMCPクライアントについては、その固有のセマンティクスが保持されます。

エージェントのバックグラウンドツールやサブエージェントのタスクには、それぞれ独自のライフサイクルがあります。実行が完了しても、結果がまだ配信されていない場合があります。その場合は、コンバーションのバックグラウンドタスクパネルを確認し、結果を収集するか、設定されているウォークアップ機能を使って親エージェントに戻す必要があります。結果がまだ表示されていないからといって、重複したタスクを開始してはいけません。

個々のツールの使用期間を超えて必要とされるコマンドについては、LSMで追跡されるジョブや、持続性のある端末を使用してください。出力結果をログファイルに保存し、ジョブの識別子を記録し、実際の進行状況を確認してください。詳細は[Usage patterns](../guides/usage-patterns.md)を参照してください。
