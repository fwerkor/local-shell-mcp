# メモリ、コンテキスト、トークンの使用量

## 3種類の異なる状態

| 国家/政府 | 目的 |
|---|---|
| 会話の履歴 | コントローラーによって保存されている、元のメッセージやツールの活動内容です。 |
| コンテキストウィンドウ | 特定のモデルリクエストで送信される、命令のサブセット、ツールのスキーマ、履歴、要約、その他のデータです。 |
| 持続的な記憶 | 再利用可能な事実や好みは、関連する記憶範囲内のさまざまな会話で利用できます。 |

長期にわたって保存されている会話内容は、モデルのコンテキストウィンドウを超えても、その履歴がすべて失われることはありません。メモリとは、アカウントの全履歴が各モデルに対して送信されるという意味ではありません。

## メモリの管理

![サンプル項目を表示したメモリ管理サイドバー](../assets/chat/memory-management.png)

メモリは、ユーザーの設定やチャットのオプション、またはデプロイメント/エージェントの機能制限によって無効にされていない限り、デフォルトで有効になっています。メモリ管理ページを使って、保存されているデータを確認したり編集したりすることができます。エージェントに、役立つ情報やプロジェクトの規則、好みなどを記憶させてもらい、メモリインターフェースでその結果を確認してください。

メモリエントリを編集する際は、小文字のみで、アンダースコアも含むキーワードを使用してください（例：`repository_conventions`）。デフォルトの文字数制限は10,000文字です。インストール時には、メモリの保存範囲を自分で設定できます。エントリが拒否された場合は、エラーの内容を確認することが重要です。秘密情報を複数のキーワードに分割するよりも、一つのキーワードにまとめる方が良いでしょう。

メモリは、Agentの設定に応じて、共有された個人用プールを使用することも、Agent固有のスコープを使用することもあります。APIキーやパスワード、その他不要な機密データは、メモリには保存しないでください。メモリを無効にすると、そのメモリが関連するスコープ内で使用されなくなります。これは、既存のデータを削除したり、会話履歴からその情報を削除したりすることとは異なります。

露出された場合、モデルは`set_memory`を使用してエントリを作成または更新します。空の値の場合は、そのエントリが削除されます。`find_memory`は、クエリや正確なキーによってエントリを取得します。また、空のクエリを使えば、保存されているメモリ一覧を表示できます。オプションの`include_conversations`フラグを使用すると、他の会話からのテキストも検索できます。ページングでは、`page`（デフォルトは1）と`limit`（デフォルトは10、最大50）が使用されます。この履歴の取得は、ツールの呼び出し記録ではなく、会話のテキストを基に行われます。取得は関連性に基づいて行われるため、必要に応じて正確な名前や用語を使ってクエリを絞り込みましょう。

自動的なメモリ/スキルの注入は、会話の各ターンにおいて一定に保たれます。これにより、再利用可能なプロバイダープロンプトのプレフィックスが保持されます。保存されているメモリを編集しても、すでに注入されたデータは変更されません。明示的なメモリの呼び出しでは、現在保存されているデータにアクセスします。新たなコンテキストが必要な場合は、新たな会話を開始することができます。

## コンテキスト容量

各モデルの実際のコンテキスト制限を、そのチャネルに設定します。Controllerは、モデルが見ることができる入力値を推定し、出力用のスペースを確保します。現在の予算の実施方法は、85％のコンパクション率と5％の予備率がデフォルトです。ただし、これは実際のモデルや実行時間の設定によって変わります。また、不慣れなトークナイザーや多様なリクエスト、またはプロバイダ固有のスキーマに対しては、この数値はおおよそのものとなります。

コンテキスト構成には、システムの指示、エージェントの設定、ツールの定義、添付ファイル、以前のメッセージやツールの結果などが含まれます。プロバイダーは、異なるトークナイザーを使用したり、追加の内部トークンを計数したりすることがあります。この表示内容は、運用上のガイダンスとして扱うべきであり、プロバイダーの保証とは見なすべきではありません。

## 自動的な圧縮処理

コンテキストの予算が削減される場合、Controllerは、以前のコンテキストに関する情報をまとめた「チェックポイントサマリー」を作成または更新します。そして、後続のモデルリクエストに向けて、最近の情報を保持します。このサマリーでは、目標、制約、決定事項、進捗状況、関連する識別子、ツールの結果、次に行うべきアクションなどが保持されます。元の保存されたデータは引き続き確認可能です。ただし、サマリーはモデルによって生成される近似値であり、完全な再現ではありません。

次のリクエストが行われる前に、コンパクションが実行されます。その際、コンテキストは縮小されます。もしサマライゼーションに失敗した場合、エンジンはエラー処理に従って再試行します。すでに過剰なサイズの入力を使って処理を続けるべきではありません。コンパクションが成功しない場合は、その状況や詳細なエラー情報を確認してください。最近のメッセージや、ツール呼び出し/結果の関係性は、常に一貫している必要があります。既に完了した古いツールの結果は、単にコンテキストを縮小するために、再書き込まれることはありません。

たとえ、一つの巨大な結果が得られたとしても、それでも予算を超えてしまう可能性があります。したがって、制限された出力範囲や、要約形式での表示などを要求することができます。また、大きな結果をファイルに保存し、必要な部分だけを取り出すことができるようにすることもできます。そうすれば、何度もモデルのコンテキストにその結果を挿入する必要はなくなります。

## 累積の使用回数と、キャッシュによるヒット数

セッションの使用状況の表示やコンテキストウィンドウの回答は、異なる意味を持ちます。入力/出力の使用状況は、会話中のすべてのモデル呼び出しにおいて累積されます。また、繰り返されるコンテキストも含まれます。キャッシュメトリクスは、利用可能な場合には、プロバイダーが報告するプランキャッシングを表します。コンテキストの占有率は、アクティブなモデルのウィンドウを示し、過去のすべての要求を合計して得られるものではありません。

例えば、20,000個の入力トークンを含むリクエストと、さらに25,000個の入力トークンを含む別のリクエストを同時に実行すると、合計で45,000個の入力トークンが使用されます。しかし、2番目のリクエストでは、現在のコンテキスト容量内で約25,000個の入力トークンしか使用されません。キャッシュされたトークンは、プロバイダーの料金体系に従わない限り、無料ではありません。モデルのコンテキスト容量が大きくなると、使用されるトークンの数も変わりますが、これは以前に使用されたトークン数とは関係ありません。

圧縮を行うと、現在の利用状況が低下する一方で、モデルの消費量は増加します。モデルを切り替えることで、適用されるコンテキストの制限が変わりますが、以前の消費量は消去されません。もしプロバイダーが正確な使用量やキャッシュメタデータを記載しない場合、推定値やメトリクスは不完全になる可能性があります。財務的な調整を行う際には、LSMの表示内容だけでなく、プロバイダーの請求データや価格情報も利用する必要があります。

## コストを削減し、有効なコンテキストを保持する。

Agentの指示を安定させること。不要な大量の出力を避け、集中して情報を取得する。関連しない作業については、別のチャットを開始してください。ハンドオフが必要な場合は、正確なパス、コミットID、観測された結果、および未解決の問題を含む簡潔なチェックポイントを保存してください。重要な情報は、生成された要約だけに頼るのではなく、元のソースやツールの結果と照らし合わせて確認してください。
