# 管理とトラブルシューティング

## 展開アーキテクチャ

WebUIのフロントエンドは、Pythonで書かれたControllerから提供されています。このControllerは、REST APIやMCPエンドポイントと同じオリジンからサービスを提供しています。デフォルトのデータベースとしてはSQLiteが使用されています。リリースされたバイナリやwheelsには、コンパイルされたフロントエンドのアセットが含まれています。ソースコードからのビルドには、JavaScript用のビルドツールが必要です。Node.jsやMongoDB、Meilisearch、そして別途デプロイされたLibreChatバックエンドは必要ありません。

[クイックスタート](../getting-started/quickstart.md)や[設定参考資料](../reference/configuration.md)を利用してください。ソースコードによるビルドについては、[WebUIのビルド手順](https://github.com/fwerkor/local-shell-mcp/blob/main/ui/workspace/README.md)を参照してください。

## 導入の確実化

信頼性の高いHTTPSリバースプロキシやトンネルを使用してください。認証や強力なセキュリティ対策も必要です。Controllerは、適切なコンテナや仮想マシン内に保持しましょう。受信するアクセスを制限し、送信する認証情報も保護してください。公開インターネット上で、認証されていないエクスポージャーを許可しないようにしてください。

プロキシは、データの処理が完了するまでバッファリングを行わずに、ストリーミング通信をサポートする必要があります。また、WebSocketを利用するインターフェースに対しても、その機能をサポートする必要があります。長時間かかるモデルやツールのリクエストには、適切な読み取り/待機時間を設定し、指定されたアップロードサイズを許容する必要があります。設定された公開URLは、ブラウザのオリジンやOAuthコールバックと一致している必要があります。TLSのエラーを解決するために、証明書チェックをグローバルで無効にしてはいけません。

リクエストは Controllerから発行されます。また、モデルに表示されるメッセージや添付ファイル、ツールの結果などは、選択されたアップストリームAPIに送信されます。機密なコンテンツを使用する前には、プロバイダーのデータ処理に関する規約を確認してください。また、外部のMCPの秘密情報やWorkerの招待トークンも保護する必要があります。

## 状態、バックアップ、アップグレード

デフォルトの状態ディレクトリは、設定されたワークスペース下の`.local-shell-mcp`です。`LOCAL_SHELL_MCP_STATE_DIR`によって、このディレクトリを変更することができます。共有データベースは`lsm.sqlite3`です。チャット内容、プロジェクト、設定情報、エージェント、メモリ、スケジュール、実行状態などはサーバー上に保存されます。アタッチメントやワークスペース内のファイルなどは、データベース外に保存されることがあります。

完全な状態ディレクトリ、設定内容、デプロイ環境/秘密情報、関連するワークスペースファイルをバックアップしてください。バックアップは機密性の高いものとして扱う必要があります。データベースのみのバックアップでは、添付ファイルや設定が省略されることがあります。静的なControllerを使用するか、一貫したSQLiteのバックアップメカニズムを利用してください。実際に使用されているSQLiteデータベースファイルのみをコピーすることで、変更された内容が保存されないようにします。バックアップを確認するには、独立したテスト環境に復元してみてください。

アップグレードを行う前には、現在のバージョン、実行パス、設定、状態の位置、実行中のジョブなどを記録してください。関連する実行処理を停止したり、安全に排出したりしてから、同じインストール環境でアップグレードを行い、認証情報、チャット履歴、モデルの生成、ストリーミング処理、Workers、スケジュールされたタスクなどを確認してください。SQLiteから古い状態への移行は起動時にサポートされています。移行が確認されるまで、従来のファイルを保持してください。実際のデータディレクトリを空のテストディレクトリに置き換えることはしないでください。

ロールバックとは、データベースのマイグレーションによって変更された状態を単に変更するだけではありません。必要な時に互換性のある状態に復元することが重要です。また、同じライブストレージ上で、独立して設定された2つのコントローラーを動かすことは避けるべきです。

## 診断：チャットが失敗しました。

| 症状 | まずは確認してください。 |
|---|---|
| UIを読み込むことができません。 | コントローラープロセス、フロントエンドバンドル、正しいURL、プロキシ、認証 |
| モデルが存在しない | チャンネル設定、モデルの検出、モデルID、アカウントの認証 |
| プロバイダからのHTTP 401/403コード | APIキー/アカウント、プロバイダーの権限、選択したチャンネルおよびプロトコル |
| HTTP 429 | 上流側のレート/クォータの制限、同時実行されるリクエストの数、アカウントやプランの状態 |
| HTTP 400/413/422 | 互換性の確保、入力データやコンテキストのサイズ、添付ファイルの制限、モデルのパラメータについての要求事項です。 |
| HTTP 5xxまたはタイムアウト | プロバイダーの状態、ネットワークの状況、サービス処理能力、プロキシのタイムアウト |
| 出力がストリーミングを停止する | 再接続/リロードを行う。生成されたエラーの詳細を確認する |
| ツールが利用できない | 機能の切り替え、エージェントの機能、マシンのACL、OAuthスコープ、コントローラーのスイッチ |
| Workerがオフライン状態 | 労働者登録、アウトバウンド接続、ハートビット、およびControllerのログ |
| 承認や質問が保留中 | チャットを開いて、要求されたアクションを確認する |
| スケジュールが実行されない | 有効な状態、タイムゾーン、エージェント/チャンネル、ターゲット、保存された認証情報、最後の実行回数 |

すべてのHTTPエラーが同じサービスから発生しているとは限りません。LSMログインに失敗した場合、アップストリームモデルAPIのエラー、外部のMCPエラー、ワーカートランスポートのエラーなど、さまざまな原因があるかもしれません。詳細なエラー情報や関連するControllerのログを確認してください。また、キーやベアラートークン、コールバックURLなどは、共有する前に暗号化しておく必要があります。

## プロバイダーの再試行と回復処理

モデルの応答が始まる前の一時的な接続エラーと一部の HTTP エラー（408, 429, 500, 502, 503, 504）は、待機時間に上限を設けて再試行できます。現在の通常の再試行間隔は 1, 2, 4, 8, 16, 30, 30, 30 秒です（初回リクエストの後に8回再試行）。HTTP Retry-After により待機時間が最大120秒まで延びる場合があり、一部のストリーミングエラーではランダムな揺らぎが加わります。再試行回数の上限はモデルリクエストごとに適用され、チャット全体での累積回数ではありません。コンテキスト圧縮には独自の復旧処理があります。クレジット不足によるレート制限はプロバイダーが枠を補充するまで続く場合があります。自動再試行は成功を保証するものではなく、サブスクリプションを無制限にするものでもありません。

途中での中断は、最初のレスポンスが行われる前のエラーとは異なります。部分的に実行されたツールの処理を自動的に再実行することはできません。再試行する前に、保存されている履歴や外部状態を確認してください。もし実行がまだ進行中であれば、重複した作業を行うのではなく、再接続してください。もし実行が失敗した場合は、チャットの回復/再試行機能を適切に使用するか、元の実行が続けられない場合は、新しいチャットを開始してください。

コンテキストの圧縮に失敗した場合は、通常のモデル生成エラーとは別に調査する必要があります。有効なコンテキストの制限、モデルの互換性、過大なツールの結果、および利用可能なクォータについて確認してください。 [記憶と文脈](context.md).

## バグ報告書に何を記載すべきか

LSMのバージョンやコミット情報、インストール方法、オペレーティングシステム、モデルプロトコル、セーフアクティブ化されたエンドポイントの種類、モデルID、推定される時間、再現手順、関連するチャットや実行状況、セーフアクティブ化された詳細なエラー情報などを報告してください。リモートでの問題がある場合は、Workerのバージョン、マシンの名前、ハートビート/POLLの状態も記載してください。可能であれば、簡単な再現手順も記載してください。APIキー、OAuthトークン、プライベートな情報や不要な個人情報は絶対に送信しないでください。
